# 보들 음성 분석 (온프레미스)

동행 매니저가 녹음한 진료 음성에서 **의사 · 환자 · 매니저**를 구분하고,
매니저가 대신 물어본 질문과 의사의 답변을 짝지어 보들 Core API로 돌려주는 서비스.

초기에는 운영자가 구분 결과를 검수하고, 그 검수가 그대로 학습 데이터가 되어
모델을 개선시킨다. 자동화는 정확도가 올라간 뒤에 넓힌다.

```
매니저 앱 (녹음)
   │
   ▼
Core API ── 오디오 ──▶ CLOVA Speech (NCP 국내 리전)
   │                      │ STT + 화자분리
   │                      ▼
   │         speaker_1/2/3 + 타임스탬프 + 텍스트
   │                      │
   │                      ▼
   │              온프레미스 AI  ← 이 저장소
   │              ① 매니저 성문 매칭 → 매니저 확정
   │              ② 나머지 역할 판정 (의사/환자)
   │              ③ Q&A 페어링 + 사전질문 대조
   │                      │
   ◀────── 구조화 JSON ────┘
   ▼
Supabase PostgreSQL → 동행 리포트
```

진료 내용 분석은 온프레미스에서 끝난다. CLOVA Speech는 NCP 국내 리전이라
국외 이전에 해당하지 않는다.

## 설계 핵심

**의사를 먼저, 따로 판정한다.** 의사와 비의사를 가르는 것이 환자와 매니저를
가르는 것보다 중요하다. 두 판정을 한 번에 최적화하면 환자·매니저 쪽 점수가
흔들릴 때 의사 판정까지 같이 흔들리므로, 의사를 독립적으로 확정하고 나머지를 배정한다.

**화자 단위로 판정한다.** 발화 하나하나를 분류하면 "네", "음..." 같은 짧은 응답에서
계속 흔들린다. 화자별로 발화를 전부 모아 한 번에 역할을 배정한다.

**매니저는 성문으로 고정한다.** 매니저는 플랫폼 소속 검증 인력이므로 자격 심사 때
음성 샘플을 받아두면 이후 모든 녹음에서 확정된다. 3명 중 1명이 확정되면 나머지는
"의사 vs 환자" 2택이 되어 난이도가 절반으로 떨어진다.

**사전 질문을 등록받는다.** 동행 요청 시 환자·보호자가 물어볼 질문을 등록하면
Q&A 매칭이 추론이 아니라 대조가 되고, 매니저가 빠뜨린 질문도 잡아낼 수 있다.

## 운영자 검수 루프

초기 정확도는 낮을 수밖에 없으므로 운영자 검수를 전제로 설계한다. 검수 결과가
학습 데이터가 되고, 그 데이터가 쌓여야 자체 모델로 넘어갈 수 있다.

운영자가 전건을 볼 수는 없으니 **신뢰도가 낮은 것부터** 큐에 올린다.
각 화자 판정에 `needs_review`가 붙고, 기준은 `REVIEW_THRESHOLD`(0.6)다.
성문으로 확정된 매니저는 검수 대상이 아니고, `UNKNOWN`은 항상 검수 대상이다.

앵커 녹음에 적용하면 이렇게 갈린다.

| 화자 | 판정 | 신뢰도 | 검수 |
| --- | --- | --- | --- |
| 참석자1 | DOCTOR | 0.77 | 통과 |
| 참석자2 | PATIENT | 0.43 | 검수 |
| 참석자3 | UNKNOWN | 0.20 | 검수 |

검수에서 쌓아야 할 것은 예측값과 정정값의 쌍이다. 정정된 역할만 저장하면
무엇이 왜 틀렸는지 알 수 없으므로, 예측 역할·정정 역할·판정 근거(`scores`)·
판정 방식(`method`)을 함께 남긴다. 이게 나중에 규칙을 고칠 때와
자체 모델을 학습시킬 때 모두 쓰인다.

## 구성

| 모듈 | 역할 |
| --- | --- |
| `src/voice_ai/clova.py` | CLOVA Speech 응답 → `Utterance` 정규화, 화자별 묶기 |
| `src/voice_ai/clovanote.py` | 클로바노트 내보내기 텍스트 파서 (API 붙이기 전 중간 입력) |
| `src/voice_ai/roles.py` | 의사 우선 판정 + 나머지 역할 배정 + 신뢰도 |
| `src/voice_ai/refine.py` | 의사 블록에 흡수된 타 화자 발화 표시 |
| `src/voice_ai/terms.py` | 의료 용어 오인식 교정 (자모 유사도 + 문서 내 근거) |
| `src/voice_ai/terminology.py` | 진료과별 용어 사전 (`data/terms/*.txt`) |
| `src/voice_ai/transcribe.py` | 녹음 파일 → SenseVoice 전사 (CLI) |
| `src/voice_ai/analyze.py` | 전사 하나를 끝까지 돌리는 진입점 (CLI) |
| `src/voice_ai/sensevoice.py` | SenseVoice 출력 정규화 (태그 제거, 언어 불일치 경고) |
| `src/voice_ai/diarization.py` | 별도 화자분리(pyannote 등) 결과를 전사와 타임스탬프로 정렬 |
| `src/voice_ai/report.py` | 의사 발언에서 리포트 초안 발췌 (생성 아님) |
| `src/voice_ai/qa.py` | 질문-답변 페어링, 사전질문 대조 |
| `src/voice_ai/models.py` | 공유 데이터 모델과 출력 계약 |

## 설치 (macOS)

가상환경을 먼저 만든다. Homebrew로 깐 파이썬은 시스템 전체 설치를 막아서
(`externally-managed-environment`) 가상환경 없이는 pip이 거부한다.

```bash
python3 -m venv .venv
source .venv/bin/activate

pip install -e ".[transcribe,dev]"
```

이후 새 터미널을 열 때마다 `source .venv/bin/activate` 한 번만 해주면 된다.
`-e .`로 설치했으므로 `PYTHONPATH`는 지정하지 않아도 된다.

<details>
<summary>Windows PowerShell</summary>

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e ".[transcribe,dev]"
```
</details>

## 전사 준비

모델 두 개를 받는다. 역시 한 번만 하면 된다.

```bash
# 음성인식
curl -L -O https://github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17.tar.bz2
tar -xf sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17.tar.bz2

# 화자분리
curl -L -O https://github.com/k2-fsa/sherpa-onnx/releases/download/speaker-segmentation-models/sherpa-onnx-pyannote-segmentation-3-0.tar.bz2
tar -xf sherpa-onnx-pyannote-segmentation-3-0.tar.bz2
curl -L -O https://github.com/k2-fsa/sherpa-onnx/releases/download/speaker-recongition-models/3dspeaker_speech_eres2net_base_sv_zh-cn_3dspeaker_16k.onnx

# 발화 구간 검출 (화자분리를 안 쓸 때만)
curl -L -O https://github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/silero_vad.onnx
```

SenseVoice는 MIT 라이선스이고 비자기회귀 구조라 Whisper Large보다 빠르다.
다만 다국어 모델이라 한국어 문장을 매끄럽게 못 붙인다. 실제 녹음에서 숫자
자체는 맞게 나왔는데("콜레스테롤이 200이 ... 216") 사이를 잇는 말이 무너졌다
("정상인데" → "정는", "작년에는" → "작년는").

한국어 전용 모델도 있다. `--engine`으로 바꿔 끼운다.

| 엔진 | 모델 | 구조 |
|---|---|---|
| `sensevoice` | `sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17` | 다국어, 비자기회귀 |
| `moonshine` | `sherpa-onnx-moonshine-tiny-ko-quantized-2026-02-27` | 한국어 전용, 인코더·디코더 |
| `zipformer` | `sherpa-onnx-zipformer-korean-2024-06-24` | 한국어 전용, transducer |
| `whisper` | `sherpa-onnx-whisper-turbo` 등 | 다국어, 인코더·디코더 |
| `faster-whisper` | HuggingFace 의 CTranslate2 모델 | 한국어 파인튜닝을 바로 끼움 |

압축을 풀면 나오는 파일 이름은 엔진마다 다르다. 받고 나서 `ls`로 확인하는
편이 확실하지만, 기준은 이렇다.

```
moonshine   encoder_model.ort            decoder_model_merged.ort      tokens.txt
              └ .onnx 가 아니라 .ort 다

zipformer   encoder-epoch-99-avg-1.int8.onnx
            decoder-epoch-99-avg-1.onnx        ← 디코더만 int8 이 아니다
            joiner-epoch-99-avg-1.int8.onnx    tokens.txt
```

whisper 는 받는 자리가 다르다. 크기 순으로 `tiny`, `base`, `small`, `medium`,
`turbo`, `large-v3` 가 있고, 한국어는 큰 쪽이 확실히 낫다. `turbo` 가
large-v3 의 속도 개선판이라 품질 대비 쓸 만하다.

```bash
curl -L -O https://github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/sherpa-onnx-whisper-turbo.tar.bz2
tar -xf sherpa-onnx-whisper-turbo.tar.bz2
```

내려받으면 `int8` 판만 들어 있다. 인코더가 675MB, 디코더가 361MB다.

30초 창으로 도는 구조라 `--max-chunk` 를 짧게 줘도 빨라지지 않는다. 남는
자리를 묵음으로 채우고 같은 시간을 쓴다. 그래서 `--max-chunk` 를 생략하면
엔진에 맞춘다(whisper 30, 나머지 10).

102초짜리 내과 재진(2인)으로 세 엔진을 같은 설정(`--speakers 3 --max-chunk 8`)
으로 돌려 견줬다.

| | sensevoice | moonshine | zipformer |
|---|---|---|---|
| 검사 수치 | 40 · 76/34 · 67/23 전부 | **76/34·67/23 없음. 40을 42로** | 42G · 6파야 42 |
| 문장부호 | 거의 없음 | 쉼표·마침표·물음표 | 없음 |
| 띄어쓰기 | 있음 | 있음 | **없음** |
| 신장/심장 | 신장 (맞음) | 심장 (틀림) | 심장 (틀림) |
| 실제 시간 | 14.2초 | 13.6초 | - |

moonshine 이 읽기에는 훨씬 낫다. 문장부호가 붙어 문장이 제대로 끊기고 Q&A
답변도 온전하게 나온다. 처음에는 이것만 보고 moonshine 으로 정했는데, 두
엔진을 맞대어 보니 **검사 수치를 통째로 흘리고 있었다.** 읽기 나쁜 것은
사람이 고칠 수 있지만("작년는"은 읽으면 안다) 없는 숫자는 녹음을 다시 듣기
전에는 되살릴 수 없다.

131초짜리 신경과 재진(3인)으로 다시 쟀다. 이번에는 whisper 를 넣고, 사람이
받아 적은 기준으로 CLOVA 전사를 함께 뒀다. **본문은 whisper 다.**

| | whisper | sensevoice | moonshine | CLOVA |
|---|---|---|---|---|
| 치매 | 0 | 0 | 0 | 2 |
| 26점 | 2 | 2 | **1** | 4 |
| 30점 만점 | 1 (안에) | 1 (만쯤) | **0** | 1 |
| MRI | 3 | 2 (엠알아) | 2 | 4 |
| 궁금해하셨 | **1** | 0 | 0 | 1 |
| 지어낸 숫자 | **없음** | 2, 4, 6 | - | 없음 |
| 통째로 흘린 구간 | 0 | 0 | **8** | 0 |

엔진마다 **틀리는 방식**이 다르고, 그게 고르는 기준이 된다.

```
whisper      글자를 빼먹는다        "지난번 이후" -> "지 이후"
sensevoice   없는 숫자를 만든다      "오셨죠" -> "50죠"
moonshine    문장을 지어낸다        "그렇죠? 그렇죠? 그렇죠?"
```

의료 기록에서는 **빼먹는 쪽이 낫다.** 빠진 것은 눈에 보이고 틀린 숫자는 보이지
않는다. whisper 는 이 녹음에서 숫자를 하나도 지어내지 않았고, 영문 약어(MRI,
B12)를 유일하게 제대로 썼다.

moonshine 은 쓰지 않는다. 8개 구간을 통째로 흘렸는데 그중 하나가 이 진료에서
제일 중요한 문장이었다("30점 만점에 26점"). 흘리지 않은 자리에서는 안 한 말을
지어냈다. 앵커에서 수치를 흘린 것과 같은 성질이고 이번에는 문장 단위였다.
zipformer 는 띄어쓰기가 없어 뒤 단계가 돌지 않는다.

맞대기는 sensevoice 로 한다. 틀리는 방식이 whisper 와 달라서 어긋난 자리를
잘 짚는다. 두 엔진에 같은 `--max-chunk` 를 주지는 않는다. whisper 는 30초,
sensevoice 는 10초가 맞아서 같은 값을 주면 한쪽이 손해를 본다. 맞대기는 15초
단위로 숫자를 견주고 용어는 녹음 전체에서 한 번씩 보므로, 구간을 다르게 끊어도
비교가 어긋나지 않는다.

**치매는 로컬 엔진 셋 다 못 받아 적었다.** CLOVA 만 잡았다. 사후 교정으로도
못 살린다. 두 글자 용어는 사전 근거만으로 고치지 않기 때문인데(`terms.py`),
그 규칙을 풀면 "보고요"가 "복통"이 되는 쪽이 열린다. 없는 증상이 리포트에
실리는 편이 치매를 한 번 놓치는 것보다 나쁘다. 남은 길은 키워드 부스팅인데,
sherpa-onnx 는 transducer 에만 지원하므로 whisper 에는 쓸 수 없다.

### 한국어 파인튜닝 모델과 용어 알려주기

`faster-whisper` 는 CTranslate2 형식이라 HuggingFace 의 한국어 파인튜닝
whisper 를 **변환 없이 바로** 불러온다. ONNX 로 바꾸는 과정이 통째로 없다.

```bash
pip install -e ".[faster]"

voice-transcribe 진료녹음.m4a \
  --engine faster-whisper \
  --model <HuggingFace 이름 또는 받아둔 폴더> \
  --department 신경과 \
  --segmentation sherpa-onnx-pyannote-segmentation-3-0/model.onnx \
  --embedding 3dspeaker_speech_eres2net_base_sv_zh-cn_3dspeaker_16k.onnx \
  --speakers 3 --out whisper.json
```

파인튜닝이 얼마나 버는지는 리턴제로가 AI-Hub 공개 테스트셋으로 재 둔
숫자가 있다. 같은 Whisper 구조에서 **11.39% → 6.59%** 로, 오류가 42%
줄었다. 우리가 "모델이 한국어를 못 알아듣는다"고 본 것이 이 차이다.

### 짧은 구간은 whisper 에 먹이지 않는다

whisper 는 30초 창으로 학습됐다. 0.3초짜리를 주면 나머지 29.7초를 묵음으로
채우는데, **디코더가 그 빈자리를 학습 데이터에서 본 문장으로 메운다.**

```
0.12초   홍 사장의 발언에 국감장이 술렁이자 조정식의 발언에 국감장이...
0.62초   고속도로 교통정보고 좋습니다
1.62초   북측에서 폭풍이 불어 닥쳤다
```

녹음에 없는 말이다. 길이로 줄 세우면 **2초 미만 18개 중 9개**가 이런 환각이고
2초 이상 19개 중에서는 1개였다. 모델이 아니라 우리가 잘게 잘라 먹여서 생긴
일이다.

길이로만 거르면 뭉툭하다. 4.37초짜리 환각("애플의 베풍과 이혼은 새 액체에
밥을 먹었습니다")은 못 걸렀고, 짧고 멀쩡한 환자 질문은 버려졌다. 환자 질문은
원래 짧다.

**모델이 스스로 알려준다.** faster-whisper 는 구간마다 세 가지를 함께 내놓는다.

## 보호자 질문

보호자는 진료실에 없다. 궁금한 것을 미리 적어 보내고 매니저가 대신 묻는다.
그래서 **질문은 녹음에서 알아내는 것이 아니라 이미 글로 가지고 있다.**

이것이 중요한 이유는, 환자 목소리가 묻혀서 질문을 한 건도 못 건졌기
때문이다. 등록 질문을 중심에 두면 그 벽을 돌아간다. 알아들어야 하는 것은
의사의 답변뿐이고, 그쪽은 가장 또렷하게 담긴다.

```
voice-analyze 전사.json --department 신경과 --questions 질문.txt
```

```
q_dizzy = 어지럼증이 약 때문인가요?
운전을 계속해도 되나요?
```

### 안 물어봤다고 단정하지 않는다

결과는 세 가지다. `물어봄`, `아마 물어봄`, `못 찾음`.

"안 물어봤다" 가 없는 것은 일부러다. 우리 전사가 약한 고리인데 그걸 근거로
매니저가 질문을 빠뜨렸다고 기록하면 사람에게 부당하다. 같은 질문이 클로바
전사로는 0.60, 우리 전사로는 0.13~0.20 이 나왔다. 한 단으로 자르면 전사가
흔들릴 때마다 누군가 일을 안 한 것이 된다.

화자분리가 매니저를 의사 쪽에 합쳐 버리는 일도 잦아서, 역할이 매니저가
아닌 발화도 후보로 본다. 대신 그렇게 찾은 것은 확정하지 않는다.

### 답변을 질문으로 잘못 잡지 않기

답변은 질문의 낱말을 되풀이한다. 겹치는 정도만 보면 1등이 답변 쪽이 된다.
"점수가 얼마나 나왔나요" 에 "점수는 26점이었습니다" 가 걸리는 식이다.

거꾸로 재면 갈린다. 답변은 질문에 없던 내용을 들고 있다.

```
                                     정방향  역방향
  의사 답변 "점수는 26점이었습니다"      0.27    0.14
  의사 답변 "치매라고 진단하지는"        0.25    0.10
  의사 답변 "약을 처방하지 않겠습니다"    0.18    0.07
  잘린 질문 "혈압약이랑 같이 드셔도"     0.35    0.67
  멀쩡한 질문 "치매로 진단된 건가요"      1.00    0.73
```

정방향은 0.27 과 0.35 로 겹쳐서 못 가른다. 역방향은 다섯 배 벌어진다.

## 잡음

실제 진료 녹음을 재니 말소리가 잡음보다 이만큼밖에 크지 않았다.

```
speaker_00  크기 0.0710  잡음보다 9.5dB
speaker_01  크기 0.0419  잡음보다 4.9dB
```

둘 다 10dB 아래다. 크기는 둘 다 정상 범위(0.03~0.1)였으니 소리가 작아서가
아니라 **묻혀서** 안 들린 것이다. 같은 녹음을 클로바는 받아 적었다.

그래서 쉬는 틈에서 잡음을 재고 주파수마다 그만큼 뺀다. 크기 하나로는 못
걷는다. 에어컨은 낮은 쪽에, 형광등은 높은 쪽에 깔린다. 다 빼지 않고 10%는
남긴다. 0으로 만들면 금속성 잡소리가 생겨 전사가 오히려 나빠진다.

재 보고 켰다. 같은 녹음에서 이렇게 달라졌다.

| 끈 쪽 | 켠 쪽 |
|---|---|
| 불**폐**한 일이 | 불**편**한 일이 |
| 목욕하거나 이 **북한** 곳에서 | 목격하거나 **익숙한** 곳에서 |
| 지난번 **협의 검사**에서는 | 지난번 **혈액검사**에서는 |
| 확인한 **값성성** 기능과 | 확인한 **갑상성** 기능과 |
| **사수** 뒤에 보겠습니다 | **사주** 뒤에 보겠습니다 |

새 환각은 하나도 생기지 않았다. 사라진 구간은 전부 잡음이 만들던 환각이다.
깨끗한 녹음이면 뺄 것이 적어 거의 그대로 간다. `--no-denoise` 로 끈다.

전에 소리를 키워 보기도 했는데 그쪽은 실패했다. 이미 충분히 컸으니 키울
것이 없었고 잡음만 커져서, 구간이 30개에서 19개로 줄고 없던 환각이 생겼다.

## 짧은 구간을 버릴지

실제 녹음의 여섯 구간으로 재 봤다.

```
                 묵음   확신   반복
환각 0.12초      0.00  -0.37   2.26
환각 0.62초      0.00  -0.80   0.79
환각 4.37초      0.00  -0.90   0.86
정상 0.86초      0.00  -0.10   0.62
정상 1.52초      0.00  -0.18   0.74
정상 9.89초      0.00  -0.10   1.37
```

**가르는 것은 확신도(`avg_logprob`) 하나뿐이었다.** 묵음 확률은 전부 0.00
이다. 말소리가 실제로 있고 모델이 그걸 잘못 받아 적은 것이라 당연하다.
되풀이 비율도 2.26 으로 기준 아래였고, 그 구간은 낱말 단위로 보는 쪽이 잡았다.

기준은 `-0.5` 다. 정상이 -0.10 ~ -0.18 이고 환각이 -0.80, -0.90 이라 사이가
넓다. 조용한 녹음으로 잰 값이고 진료실은 더 시끄러울 테니 바짝 조이지 않는다.
묵음 확률과 되풀이 비율은 다른 종류의 실패를 위한 그물로 남겨 둔다.

이렇게 거르면 **짧아도 확신하면 남기고 길어도 지어낸 것이면 버린다.**
길이는 0.6초 아래만 막는다. 그보다 짧은 것은 화자분리가 남긴 부스러기라
어차피 건질 것이 없다.

sherpa 쪽 `whisper` 엔진은 그 신호를 꺼내 쓸 수 없어 2초로 막는다.

같은 말이 세 번 넘게 되풀이되면 디코더가 구멍에 빠진 것으로 보고 버린다.
moonshine 의 "그렇죠? 그렇죠? 그렇죠?" 와 같은 모양이다. 말을 더듬어 한
낱말을 두 번 한 것("익숙 익숙한 곳에서")은 구멍이 아니므로 남긴다.

### 용어 알려주기는 끄고 쓴다

whisper 는 디코더에 미리 말을 알려줄 수 있다(`hotwords`). 사후 교정으로 못
살리는 자리를 오인식 전에 막자는 생각으로 붙였는데, **실제 녹음으로 재 보니
모델이 망가졌다.**

```
용어 없이   안녕하세요 지난번 이후 기업력 때문에 불폐한 일이 있었나요
용어 60개   <아무것도 안 나옴>
용어 12개   "이 아홉 명의 발언에 제기되었습니다" 가 아홉 번
```

12개로 줄여도 소용없었다. 녹음에 없는 말을 지어내고 같은 말을 되풀이한다.
디코더 프롬프트에 무엇을 넣든 모델은 그쪽으로 끌려가는데, 의료 용어를 끼워
넣으려다 문장 전체를 잃으면 얻는 것보다 잃는 것이 크다.

**그래서 기본으로 켜지 않는다.** 모델마다 다를 수 있으므로 길은 남겨 뒀다.
쓰려면 `--hotwords "치매, 편두통"` 처럼 직접 주고, **짧은 구간으로 먼저 재
봐야 한다.** 전체를 돌린 뒤에야 알면 몇 분을 버린다.

모델을 고를 때 볼 것:

- **학습 데이터와 라이선스.** AI-Hub 데이터로 학습했다면 이용 조건을 확인해야
  한다. 승인 절차와 상업적 이용 조건이 데이터셋마다 다르다.
- **base/small 말고 medium 이상.** 작은 모델은 파인튜닝해도 한계가 있다.
- 모델 카드에 **무엇으로 얼마나** 학습했는지 적혀 있는 것.

한국어 ITN(`rule_fsts`)과 호모폰 교정(`hr_*`)은 sherpa-onnx에 있긴 하지만
중국어 전용이다(`itn_zh_number.fst`뿐이고, 호모폰 교정기는 한자가 아니면
건너뛴다). 한국어에는 쓸 수 없다.

## 실행

녹음 하나를 끝까지 돌리는 데 명령이 셋 필요하고 경로가 길다. 한 줄로 묶어 뒀다.

```bash
source .venv/bin/activate
VOICE_MODELS=~/models ./scripts/run.sh 진료녹음.m4a 내과 2026-10-02
```

본문은 whisper, 맞대기는 SenseVoice 로 돌리고 어긋난 자리를 표시한다. 모델이
하나라도 없으면 전사를 시작하기 전에 어느 파일이 없는지 알려준다.

결과는 녹음 파일 옆에 쌓인다. 녹음을 어디 두든 한 건이 한 폴더에 모인다.

```
~/Desktop/bodeul-voice/진료녹음.m4a
~/Desktop/bodeul-voice/진료녹음/
    whisper.json  본문 전사
    sense.json    맞대기 전사
    report.txt    사람이 읽는 분석
    report.json   Core API 로 넘길 형태
```

`VOICE_OUT` 으로 다른 곳에 보낼 수 있다. 저장소 안에 두더라도 전사 결과는
`.gitignore` 가 막지만, 실제 진료 음성이면 녹음 자체도 저장소 밖에 두는 편이
안전하다.

인원을 알면 `VOICE_SPEAKERS` 로 알려준다. 기본값은 3이다.

```bash
VOICE_SPEAKERS=2 VOICE_MODELS=~/models ./scripts/run.sh 진료녹음.m4a
```

아래는 그 안에서 실제로 도는 명령이다. 따로 바꿔 끼울 때 쓴다.

두 단계다. 녹음 파일을 전사하고, 전사를 분석한다.

```bash
voice-transcribe 진료녹음.m4a \
  --engine whisper \
  --encoder sherpa-onnx-whisper-turbo/turbo-encoder.int8.onnx \
  --decoder sherpa-onnx-whisper-turbo/turbo-decoder.int8.onnx \
  --tokens sherpa-onnx-whisper-turbo/turbo-tokens.txt \
  --segmentation sherpa-onnx-pyannote-segmentation-3-0/model.onnx \
  --embedding 3dspeaker_speech_eres2net_base_sv_zh-cn_3dspeaker_16k.onnx \
  --speakers 3 --out whisper.json

voice-analyze whisper.json
```

`--speakers`로 인원을 알려준다. 생략하면(`-1`) 거리 기준으로 알아서 나누는데,
102초짜리 실제 진료 녹음에서 **화자를 7명으로 쪼갰다.** 짧은 맞장구("네", "예")마다
새 화자를 만든 것이다. 1초 남짓한 음성에서 뽑은 성문은 믿을 게 못 된다.

같은 파일에 2, 3, 4를 각각 준 결과는 **셋 다 동일했다**(화자 2명, 24구간). 실제
목소리가 2개뿐이라 남는 클러스터에는 짧은 조각만 배정됐고, 그 조각들은
`min_duration_on`(0.3초)에 걸려 전부 버려졌다. 넉넉하게 부르는 쪽은 이 녹음에서
손해가 없었다.

다만 이건 2인 녹음으로 확인한 것이다. 3인 이상에서 남는 클러스터가 실제 발언을
몇 초씩 가져가면 없는 사람이 생기고 의사 발언이 그쪽으로 넘어간다. 3인 녹음이
생기면 다시 재야 한다.

과분할이 의심되면 분석 단계에서 `--merge-non-doctor`로 비의사 화자를 합친다.
역할 표시만 정리되는 것이 아니다. `pair_qa`는 질문자가 MANAGER나 PATIENT일 때만
페어링하므로, UNKNOWN으로 남은 화자의 질문은 통째로 버려진다. 실제 녹음에서
합치는 것만으로 Q&A가 0건에서 1건이 됐다.

화자분리 없이 VAD로만 끊을 수도 있지만(`--vad silero_vad.onnx`), 실제 녹음에서
구간 경계가 화자 전환점과 어긋나 의사 발언 끝에 환자 응답이 붙었다. 역할 판정이
목적이라면 화자분리를 쓰는 편이 낫다.

`--threads`는 전사와 화자분리 양쪽에 쓰인다. Apple Silicon이면 성능 코어 수에
맞춰 올린다(M1/M2 기본형은 4).

측정값(M 시리즈 Mac mini, 8스레드, 102.5초 녹음):

| | 값 | 뜻 |
|---|---|---|
| CPU 시간 | 100.9초 = 실시간의 0.98배 | 서버 코어 수를 정하는 값 |
| 실제 시간 | 14.2초 = 실시간의 0.14배 | 매니저가 기다리는 시간 |

10분 진료면 8코어에서 약 85초. 하루 100건이라도 CPU 17시간 남짓이라 작은
서버로 충분하다. 비싼 쪽은 전사가 아니라 화자분리다. 창을 10%씩 밀며 반복
추론하기 때문이다.

### 매니저 성문

의사·환자·매니저를 가르는 일에서 **유일하게 전사 품질과 무관한 자리**다.
나머지는 글자가 깨지면 같이 무너진다. 성문은 오디오만 본다.

실제 3인 녹음에서 화자분리가 의사는 깨끗이 갈라냈지만 환자와 매니저를 한
덩이로 묶었다. 목소리가 셋 다 구분되는 녹음이었는데도 그랬다.

매니저는 플랫폼 소속 검증 인력이라 자격 심사 때 음성 샘플을 받아둘 수 있다.
한 번 받아 두면 이후 모든 녹음에서 확정되고, 3명 중 1명이 확정되면 나머지는
"의사 vs 환자" 2택이 되어 난이도가 절반으로 떨어진다.

```bash
voice-enroll 김승민 샘플1.m4a 샘플2.m4a \
  --embedding 3dspeaker_speech_eres2net_base_sv_zh-cn_3dspeaker_16k.onnx \
  --out 매니저_김승민.json

voice-transcribe 진료녹음.m4a ... --manager 매니저_김승민.json
```

샘플은 여러 개 주는 편이 낫다. 하나만 쓰면 그날 목소리 상태에 끌려간다.
전사 파일에 `is_manager` 가 붙고, `voice-analyze` 가 그 화자를 매니저로
고정한 채 나머지를 배정한다.

**닮은 화자가 없으면 아무도 배정하지 않는다.** 매니저가 말을 거의 안 한
진료도 있고, 그때 환자를 매니저로 고정하면 역할이 통째로 뒤바뀐다. 기준은
코사인 유사도 0.55다.

성문은 한 번에 하나만 받는다. 매니저가 여럿이어도 **누구를 맞춰볼지는 부르는
쪽이 정한다.** 동행 세션에는 배정된 매니저가 한 명이므로 Core API 가 그
매니저의 성문을 넘기면 된다. 여러 성문을 놓고 누구인지 찾는 일(1:N)이 아니라
한 사람이 맞는지 확인하는 일(1:1)이라 훨씬 안정적이고, 매니저가 늘어도
느려지지 않는다.

```
동행 세션 ─ manager_id ─▶ 매니저 성문 조회 ─▶ --manager 로 넘김
```

화자분리가 매니저를 두 덩이로 쪼갠 경우는 아직 다루지 않는다. 가장 닮은
한 화자만 고정한다.

### 핵심 내용

리포트 초안은 의사 문장을 발췌하므로 전사의 깨진 어미가 그대로 따라온다.
"40 이상 보다 높 으니까" 같은 줄은 보호자에게 보여줄 수 없다. 매끄럽게 고치려면
생성형이 필요한데, 그러면 잘못 전사된 수치가 그럴듯한 다른 값으로 바뀐다.

그래서 문장 대신 값을 뽑는다. 이름표는 우리가 붙이고 값은 원문에서 그대로
가져오므로 지어내는 부분이 없고, 깨진 어미는 값이 아니라 따라오지 않는다.

```
[검사 수치]
  콜레스테롤  (시점은 다른 엔진)
      정상     200
      시점없음  216
  간수치      (검사명 추정)
      정상     40
      작년     76 / 34
      이번     67 / 23
[진단·소견]        고지혈증, 지방간, 내장지방
[이상 없다고 한 항목]  빈혈
[복용]             간보호제   매일 / 하루에 하나   두 달분
[생활 지도]        허리 줄이기, 술 줄이기, 체중 줄이기, 운동
```

복용 주기와 기간도 걸린 부분만 떼어낸다. 문장을 통째로 실으면 "하루에
하나하시면만 드시면 되니까" 처럼 깨진 어미가 따라온다.

생활 지도 대상은 공통 사전의 `[lifestyle]` 표준 이름으로 모은다. 전사가
"허리리", "운동부" 로 흔들리면 같은 지도가 여러 이름으로 흩어지기 때문이다.
사전에 없는 말은 들린 대로 둔다. 의사가 무엇을 줄이라 했는지 버릴 수는 없다.

약품은 용어 교정을 반영한 뒤에 찾는다. "간보제"는 사전에 없고, 그것이 바로
교정이 잡아낸 오인식이다.

점수로 말하는 검사는 따로 받는다. 검사 수치는 이름이 먼저 나와야 숫자를
받는데(그 사전 대조가 환각 숫자를 막는다), 점수는 이름 없이 온다.

```
지난 검사 점수는 30점 만점에 26점이었습니다
  -> [점수] 검사 점수   저번   26점 / 30점 만점
```

`점`이라는 단위 자체가 근거다. 눈금 설명("가장 심한 통증을 10점으로 해서
적으세요")은 측정값이 아니므로 뺀다. 올리면 없던 통증 기록이 남는다.

한글로 쓴 점수도 읽는다. 한국어 파인튜닝 모델은 숫자를 한글로 쓴다
("이십 육 점"). 전사가 제일 좋은 모델인데 숫자를 못 읽으면 그 장점이 통째로
날아간다.

**`점`이 바로 뒤에 붙었을 때만 읽는다.** 단위 없이 읽으면 "검사"의 사가 4가
되고 "지금"의 이가 2가 된다. 앞에 한글이 붙어 있어도 낱말의 일부다. 날짜에서
한글 숫자를 막아 둔 것과 같은 이유인데, 점수는 `점`이라는 안전한 기둥이 있어
열 수 있다.

**`점수`는 단위가 아니라 낱말이다.** 전사가 "비타민 B12"를 "비타민 비시 이
점수치"로 흘렸고 그 "이"가 2점으로 올라갔다. 숫자 쪽에도 같은 덫이 있다
("비12 점수").

누구 말을 받을지는 숫자의 주인으로 가른다. 검사 점수의 주인은 검사 결과이므로
의사 말만 받는다. 실제 녹음에서 환자가 자기 점수를 29점으로 잘못 기억하고
있었다. 아픈 정도의 주인은 환자 본인이므로 통증 점수는 환자 말도 받는다.
의사 말만 보면 통증 점수는 영영 못 잡는다.

수치는 시점별로 가른다. 나열만 해서는 좋아졌는지 나빠졌는지 읽을 수 없는데,
보호자가 알고 싶은 것이 그것이다. 한국어는 방향이 섞여서, 기준값은 숫자가
앞에 오고("40이 정상") 시점은 뒤에 온다("작년에는 76"). 기준값을 먼저 떼지
않으면 "40 이상 보다 높으니까"의 40이 직전 시점으로 딸려간다.

어미가 다 무너진 전사에서도 결과가 같았다. 시점 단어는 대체로 살아남는다.
시점 표현을 통째로 흘린 경우에는 다른 엔진 전사에서 빌린다. 실제로
SenseVoice 가 "정상"을 "정는"으로 흘렸고 moonshine 은 "정산"으로 들어
살릴 수 있었다. 빌리는 것은 시점뿐이고 근거 문장은 늘 본문 것을 쓴다.

숫자가 어느 검사의 것인지는 같은 구간에 함께 나왔다는 것 말고 근거가 없다.
그래서 근거 문장을 늘 같이 남기고, 검사 이름을 앞 구간에서 이어받았을 때는
`(검사명 추정)` 으로 표시한다.

"괜찮다"고 말한 항목은 진단과 나눈다. "빈혈은 괜찮으시고"를 진단에 올리면
없는 병이 기록에 남는다.

### 누가 무엇을 받는가

`--json` 출력은 두 쪽으로 나뉜다.

| | 받는 것 |
|---|---|
| 매니저 | `speakers`, `qa_pairs`, `facts`, `report_draft` |
| 관리자 | `operations` (종류별 개수 + 원문) |

경고는 매니저에게 보내지 않는다. 매니저는 진료실에서 환자 옆에 있고,
"화자분리가 한 사람을 쪼갰을 수 있습니다" 같은 말로 그 자리에서 할 수 있는
일이 없다. 사전을 고치고 엔진을 바꾸는 것은 운영하는 쪽의 일이다.

관리자에게도 진료 한 건마다 산문을 읽게 하지 않는다. 필요한 것은 여러 건에
걸친 추세다. 어느 진료과에서 판정이 흔들리는지, 어떤 용어가 자주 엇갈리는지는
세어 봐야 보인다.

```
운영 점검 (관리자용 · 매니저 화면에는 내보내지 않는다)
  number_disagreement 2  term_correction 2  term_disagreement 8
```

다만 숫자 불일치만은 그 자리에 있던 사람만 풀 수 있다. 관리자는 녹음을 다시
듣는 수밖에 없고 매니저는 기억할 수도 있다. 경고로 띄우는 대신 리포트 칸에
확인 표시를 붙이는 쪽이 맞아 보이는데, 아직 정하지 않았다.

### 전체 대화 보기

`--full` 을 주면 발췌 대신 전체 대화를 화자와 함께 보여주고, 용어 교정을
본문에 반영한다. 원문은 지우지 않고 괄호로 남긴다.

```
[01:06] DOCTOR  간수치(←반수치가) 좋아지려면 저 간보호제(←감보제) 드시던 거
```

고친 글과 실제로 들린 것을 한 화면에서 봐야 판단할 수 있다. 원문을 지우면
매니저가 녹음을 다시 듣기 전에는 근거가 없어진다.

### 두 엔진을 맞대기

엔진마다 다른 자리에서 틀린다. 실제 녹음에서 SenseVoice 는 "신장"을 맞추고
moonshine 이 "심장"으로 썼으며, 숫자를 잇는 말은 반대로 moonshine 이 나았다.

화자분리는 오디오만 보므로 한 번만 돌리면 되고, 전사만 두 번 한다. 같은 구간을
먹이니 시간이 그대로 맞아 비교가 간단해진다.

```bash
voice-analyze whisper.json --department 신경과 --compare sense.json
```

숫자와 의학 용어가 엇갈리는 자리를 경고로 알린다. **엇갈리지 않으면 아무 말도
하지 않는다.** 두 엔진이 독립적으로 같은 숫자를 냈다는 뜻이고, 그게 검증이다.

구간을 짝지어 비교하지는 않는다. 엔진마다 빈 결과를 내는 구간이 달라 나누기가
어긋나기 때문이다. 용어는 녹음 전체에서 한 번씩, 숫자는 15초 단위로 견준다.
구간끼리 짝지었을 때는 긴 구간 하나가 상대의 11개와 겹치면서 같은 발견이
11번 나왔다.

두 전사는 같은 설정으로 만들어야 한다. 한쪽만 `--max-chunk` 를 준 채로 견주면
차이가 엔진 탓인지 설정 탓인지 알 수 없다.

합치지는 않는다. 두 전사를 섞으면 아무도 말하지 않은 문장이 만들어진다. 한쪽을
본문으로 쓰고 어긋난 자리만 표시한다.

전사를 이미 갖고 있다면 1단계를 건너뛴다.

```bash
voice-analyze 클로바노트내보내기.txt
voice-analyze chunks.json --json
```

`--department 내과`처럼 진료과를 주면 그 과 용어 사전을 함께 쓴다. 공통 사전은
언제나 들어간다. 사전이 클수록 엉뚱한 교정이 늘어서 진료과로 나눠 뒀다.

## 용어 사전

`src/voice_ai/data/terms/*.txt`에 진료과별로 둔다. 파일을 하나 더 만들면 바로
`--department`로 고를 수 있다.

```
[drug]
간보호제

[condition]
지방간

[test]
간수치
```

약품과 질환·검사를 나누는 이유는 리포트 약품란에 병명이 들어가지 않게 하기
위해서다. 처음에 한 덩어리로 뒀다가 약품란에 "고지혈증, 콜레스테롤, 피검사"가
들어갔다.

**발음이 비슷하면서 뜻이 전혀 다른 말은 둘 다 넣어야 한다.** 실제 녹음에서 신장(콩팥)이
심장으로 전사된 적이 있는데, 한쪽만 사전에 있으면 교정이 오히려 뜻을 바꿔 버린다.

## 실제 녹음에서 배운 것

진료 녹음 1건(클로바노트 전사)을 앵커로 돌려보고 세 가지를 고쳤다.
`tests/test_clovanote.py`가 같은 구조를 합성 데이터로 재현해 고정하고 있다.

**환자도 질문한다.** 처음에는 질문 비율이 높으면 매니저로 봤는데, 재진 상담에서
환자가 자기 상태를 직접 물었다("저번이랑 비교해서 많이 나빠진 건가요?").
구조 특징은 어휘 근거를 보강만 하고 역할을 새로 만들지 못하게 했다. 질문한다고
매니저가 아니라 대리 질문 화법이 있어야 매니저다.

**환자는 증상을 호소하지 않는다.** 재진에서는 설명을 듣고 짧게 반응하는 쪽이다.
1인칭 증상 신호만 보던 것을 수용 반응("알겠습니다", "해야겠네요")과
자기 행위 서술("~기는 해요")까지 넓히고, 비의료인 화자의 기본값을 환자로 뒀다.

**판정 불가를 인정해야 한다.** 마지막에 인사말만 남긴 화자는 어휘 신호가 0이었다.
억지로 배정하는 대신 `UNKNOWN`과 경고로 넘긴다. 신뢰도도 전역이 아니라 화자별로
계산한다. 판정 불가 화자 하나가 의사 판정의 확신까지 끌어내리면 안 된다.

## 출력 계약은 `session_reports`에 맞춘다

보들에는 이미 동행 특화 리포트 스키마가 있다(`bodeul.session_reports`,
"동행 종료 시 매니저가 작성하는 진료와 복약 결과의 PostgreSQL 운영 원본").
일반적인 SOAP 노트 대신 이 컬럼들을 그대로 채운다. `ReportDraft`가 1:1 대응이다.

매니저가 손으로 쓰던 리포트를 AI가 초안으로 채우고 매니저가 확정하는 구조다.
제품 흐름에도 맞고, 판단 책임이 사람에게 남는다는 점에서도 맞다.

주의할 것이 둘 있다.

- `companion_session_artifacts.purpose`는 현재 `PAYMENT_EVIDENCE`와
  `PRESCRIPTION_IMAGE`만 허용한다. 진료 음성을 여기 보관하려면 마이그레이션이 필요하다.
- 녹음·분석 동의는 기존 `consent` 도메인(`GuardianSharingConsent`)에 붙이는 것이
  자연스럽다. 건강정보는 민감정보라 별도 동의가 필요하다.

## 아직 확인되지 않은 것

- **용어 사전 확보.** `terms.py`가 오인식을 잡아내려면 약품·질환·검사명 사전이
  있어야 한다. 진료과별로 실제 쓰이는 용어를 모으는 일이 남아 있다.
- **구어체 정리.** 전사 원문은 필러와 중복이 많아 그대로 리포트에 쓸 수 없다.
  정리는 LLM이 맡되 원문을 반드시 함께 보관한다. 의료 기록이라 대조가 가능해야 한다.

## 화자분리는 필수가 아니다

앵커 전사문에서 화자 라벨을 전부 지우고 문장만 남긴 뒤 점수로만 갈라봤다.

```
전체 33문장   판정 21   정답 21   오답 0
정확도 100%   커버리지 64%
```

판정하지 못한 문장은 "네", "맞습니다", "그럼요" 같은 짧은 맞장구다. 텍스트에
단서가 없어 원리적으로 가를 수 없지만, **리포트에 담을 내용도 없어 손해가 아니다.**
수치·약·일정·지시사항은 전부 긴 발화에 있고 거기는 신호가 풍부하다.

넓게 먹히는 신호는 **주체 높임**이었다. 의사는 환자의 행위를 높이고("드시면",
"줄이셔야", "높으시니까") 환자는 자기 행위를 높이지 않는다("먹기는 해요",
"알겠습니다"). 이 방향성 하나로 커버리지가 크게 올랐다.

예외가 하나 있다. **인사말에서는 환자도 상대를 높인다**("추석 잘 보내시고요").
주체 높임이 뒤집히는 유일한 자리라 인사말은 분류에서 뺀다. 리포트에 쓸 내용도 없다.

그래서 최소 구성은 이렇게 된다. 화자분리 모델도 GPU도 성문 등록도 없다.

```
녹음 → STT → sentence_role() 로 문장별 판정 → Q&A 페어링 → 리포트 초안
```

화자분리는 나중에 정확도가 부족할 때 얹는 선택지다. 특히 환자와 매니저를
갈라야 할 때 필요해지는데, 그 구분은 의사 분리보다 우선순위가 낮다.

## STT와 화자분리는 갈아끼울 수 있다

`clova.py`, `clovanote.py`는 어댑터다. 하는 일은 외부 출력을 `Utterance` 목록으로
바꾸는 것뿐이고 역할 판정·Q&A 페어링·용어 교정은 그 아래에서 돈다. 다른 STT나
화자분리로 바꿔도 어댑터만 추가하면 된다.

화자분리를 따로 쓰면 `diarization.align`이 전사와 화자 구간을 타임스탬프로 맞붙인다.
여기서 CLOVA의 구조적 한계 하나가 풀린다. CLOVA는 세그먼트마다 화자를 하나만 붙여서
긴 의사 설명에 끼어든 환자의 짧은 응답을 표현할 방법이 아예 없었다. 화자 구간을
따로 받으면 한 전사 구간이 두 화자에 걸친 것을 알아낼 수 있다.

정렬은 화자를 붙이고 혼입을 경고할 뿐 텍스트를 쪼개지 않는다. 단어 단위 시각 없이
문장을 나누면 어느 쪽 화자의 말인지 잘못 가를 수 있다.

## 의료 용어 오인식 교정

앵커에서 "간 보호제"가 같은 대화 안에서 한 번은 맞게, 한 번은 "관보제"로 전사됐다.
사람이 이걸 알아보는 근거는 셋이다. 올바른 형태가 같은 문서에 이미 나왔고,
발음이 비슷하고, 문맥이 간 이야기였다. 앞의 둘은 규칙으로 재현된다.

한글을 자모로 풀고(겹모음까지 분해해야 간/관이 거리 1로 잡힌다) 사전 용어와의
유사도를 잰다. 올바른 형태가 같은 전사문에 이미 있으면 `IN_DOCUMENT`로 표시하는데,
이게 가장 믿을 만한 근거다. 같은 진료에서 같은 약을 두 번 말하는 일은 흔하고
STT가 두 번 다 똑같이 틀리는 일은 드물다.

한쪽이 다른 쪽을 품고 있으면 건너뛴다. "지방간은"은 오인식이 아니라 조사가 붙은
것이고 "복부내장지방"은 더 큰 말의 일부다. 이 규칙 하나로 앵커의 오탐 5건이 사라졌다.

발음 유사도로 못 잡는 자리는 **들린 말을 손으로 적는다**. 같은 녹음에서
"치매"를 네 엔진이 전부 다르게 틀렸는데 유사도 1위가 전부 엉뚱했다.

```
치밀하고 -> 치매약 0.500      치고 -> 치매약 0.545
짐으로   -> 이명   0.500      심이 -> 이명   0.600
```

기준을 낮추면 치매 대신 **치매약(약품란!)과 이명**이 들어온다. 두 글자 용어라
사전 근거만으로는 고치지 않는 규칙에도 걸린다. 사전의 `[misheard]` 에
적어 두면 그 짝만 고친다.

```
[misheard]
침해 = 치매
엠알아 = MRI
```

**다른 뜻으로도 쓰이는 말은 적지 않는다.** "치고"는 "~치고는"이 있어서 뺐다.
교정은 제안일 뿐 덮어쓰지 않지만, 운영자를 헷갈리게 하면 안 된다.

**교정은 제안만 하고 원문을 덮어쓰지 않는다.** 약 이름을 잘못 고치면 리포트가
조용히 틀린 채로 나간다. 확정은 운영자가 한다.

다만 이건 사후 교정이다. **먼저 할 일은 CLOVA Speech 키워드 부스팅에 용어를
등록해서 오인식 자체를 줄이는 것이다.** `terms.py`는 부스팅이 놓친 것을 받는 그물이다.

## 화자분리 오류 대응

앵커에서 두 가지가 실제로 확인됐다.

**흡수.** 긴 의사 설명 안에 환자의 짧은 응답이 통째로 들어가 있었다
("운동 열심히 해야겠네요", "알겠습니다"). CLOVA는 세그먼트마다 화자를 하나만 붙인다.
`refine.flag_foreign_sentences`가 역할 확정 후 역방향으로 훑어 이런 문장을 표시한다.
표시만 하고 재배정하지는 않는다. 한 문장으로 화자를 단정하기에는 근거가 얇고,
잘못 옮기면 의사 발언과 환자 발언이 뒤바뀌어 리포트가 틀어진다.

**과분할.** 한 사람이 여러 화자로 쪼개져 나왔다(앵커의 참석자 2와 3은 같은 사람).
`classify(merge_non_doctor=True)`로 비의사 화자를 한 사람으로 합쳐 판정한다.
의사만 정확히 갈라내면 되므로 이 병합은 목적을 해치지 않는다. 다만 텍스트만으로
동일인 여부를 알 수는 없어 호출자가 판단해 넘겨야 한다. 자동 판단에는 성문이 필요하다.

## 현재 상태와 다음 작업

지금은 **규칙 기반 베이스라인**이다. 남은 작업:

1. **CLOVA 응답 스키마 확정** — `clova.py`는 `speaker.label`과 `diarization.label`을
   모두 받아들이는 방어적 파싱 상태다. 실제 응답을 픽스처로 넣고 좁혀야 한다.
2. **매니저 성문 운영 연결** — 등록·매칭은 붙었다(`voice-enroll`, `--manager`).
   플랫폼이 자격 심사 때 샘플을 받아 두고 분석 때 성문 파일을 넘겨주면 된다.
3. **온프레미스 LLM 연결** — 규칙 점수를 사전 확률로 넘기고 최종 판정과 요약을 맡긴다.
4. **화자분리 오류 보정** — 역할 확정 후 역방향으로 오배정 발화를 재배정한다.
5. **HTTP 계층** — Core API가 호출할 엔드포인트.
